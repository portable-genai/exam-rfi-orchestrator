# COMPLIANCE: Regulatory Exam and RFI Orchestrator (`exam-rfi-orchestrator`)

Maps every catalog principle (P-01 to P-13) and every platform dependency rule (R1 to R8) to a
control in THIS repo, with the file that is the evidence. Aligned to MAS TRM, APRA CPS 234 and
CPS 230, HKMA and PDPA-class regimes; the regulatory crosswalk itself is adopter-owned (see the
last section).

## How to read the status column

| Status | Meaning |
|---|---|
| **Covered** | The control exists in this repo and a test fails the build if it regresses. |
| **Partial** | The in-repo half exists; the named deploy-time or platform half does not yet. |
| **TODO (repo owner)** | NOT covered. The row names exactly what this repo must add. A rendered repo starts here on several rows by design, because the control depends on the vertical or on the deployment, and claiming it before it exists would be worse than owing it. |
| **n/a** | The principle does not apply to what this service does. State WHY, and revisit if the scope changes. |

A rendered repo is honest on day one, not complete on day one. Close the TODO rows before this
document is cited as evidence to a second or third line of defence.

## Cross-cutting controls

| Area | Status | Evidence |
|---|---|---|
| Supply chain | Covered | Committed `requirements-dev.lock` and `requirements-gcp.lock`, installed with `--no-deps` by `make install`, CI and the Dockerfile, with the catalog commons pinned to 40-character COMMIT shas (a tag can be moved, so a tag pin lets what installs change with no diff); digest-pinned base image; SHA-pinned Actions; dependabot per ecosystem; `pip-audit` as a hard CI failure. `tests/unit/test_repo_artifacts.py` asserts each of these from inside the repo. |
| Fail-closed configuration | Covered | The profile resolves THREE states into a `ProfileChoice`: unset is NO CHOICE (never a silent `local`), an emptied value and an unknown or mis-capitalised one both raise AT IMPORT, so a process fails to boot rather than serving on a posture nobody chose. Relaxations key off the derived `exposure_profile` and the loopback bound off the derived `bind_profile`, because the two fail closed in opposite directions. Only `config.py` may read the variable; `tests/unit/test_profile_single_source.py` fails the build if a second module re-derives it, and `tests/unit/test_three_state_env_reads.py` fails it for ANY two-state environment read in shipped code, which is how a two-state read of a different variable stops being invisible. |
| Secret handling | Covered | No secret value is committed. `config/settings.yaml` and `.env.example` carry names and non-secret defaults; `.env.secrets.example` carries placeholders. Inbound and outbound credentials are deliberately distinct variables. |
| Browser boundary (`ui/`) | Covered | The client never asserts identity: every client-supplied actor, tenant, role, ACL and authorization header is discarded before forwarding (`ui/lib/embed-policy.mjs`), identity is resolved server-side (`ui/lib/identity-policy.mjs` behind `ui/lib/server/identity.ts`), and the service credential is read from the server environment so it never reaches a bundle. Every environment read behind that boundary resolves three states like the service's own: unset REFUSES a `UI_PROFILE` rather than seeding a dev persona, and an emptied `UI_PROFILE`, `UI_FRAME_ANCESTORS`, `UI_TENANT_ORIGINS` or `AGENT_API_URL` refuses rather than inheriting the unset default, the two allowlists doing so from `next.config.mjs` so a UI whose allowlist rendered empty never boots. Framing and CORS are per-tenant allowlists that refuse a wildcard; an unset tenant allowlist denies. The outbound `AGENT_S2S_TOKEN` is deliberately two-state, matching `hex_service_kit.s2s.client_headers`, because the receiver decides. Proved by `ui/tests/embed-policy.test.mjs` and `ui/tests/identity-policy.test.mjs` in the ui-gate workflow, guarded against regression by `ui/tests/three-state-env-reads.test.mjs` (which scans every shipped `.mjs`/`.ts`/`.tsx` in `ui/`, the blind spot that let a wildcard-CORS two-state read survive the whole gate), and held to the wall by `tests/unit/test_ui_surface.py` in the offline gate. N/A once `make drop-ui` has run. |
| Demonstrability | Covered | The demo is code and every narrated claim is asserted (`make demo-selftest`), the portability claim is executable and bounded (`make portability`), and the hosted check runs both on every pull request and every push to main. A claim that stops being true fails a build rather than a meeting. |
| Tenant isolation and object-level authorisation | Partial | The tenant partition is carried on every outbound review, and the case store now filters rows by tenant AND by the reader's entitlements IN THE QUERY (`adapters/local/case_store.py`), which is where object-level authorisation from data tags lands. Retrieval is filtered the same way: a document is readable only when its ACL labels are a subset of the server-verified entitlements, decided in the pure domain and re-checked after the store (`domain/coverage_engine.py` rule A1). What REMAINS: the managed Firestore case store is unwired, so the query-level filter is proved offline only, and nothing here verifies that the identity provider actually populates the principals claim. |

## Adopter-owned crosswalk

The mapping above is to the catalog's own principles and rules. The mapping from those to a
specific regulation, and the decision that a control is SUFFICIENT for that regulation, is
adopter-owned: it depends on the institution's risk appetite, its regulator, its licence
conditions and its existing control library. This repo does not make that claim on an adopter's
behalf, and no row above should be quoted as regulatory assurance.

What an adopter is expected to add, in their own control library rather than in this file:

- the crosswalk from each row above to their MAS TRM, CPS 234, CPS 230, HKMA or PDPA control ids;
- the risk acceptance for every row still marked Partial or TODO at go-live;
- the second-line review of the deterministic policy in `domain/`, which is bank-owned logic and
  not a vendor default to be inherited unexamined;
- the retention schedule and the legal basis for the audit trail this service writes;
- **one row per named regime** in `policy.regime_register`: the regime id, the public source the
  notice cites, and whether it fixes a response window. EVERY shipped row says it does NOT, so the
  notice's own date governs; rule K3 ships live and unit-tested precisely so an adopter whose
  counsel identifies a regime that DOES fix one configures it rather than patching code, and the
  due basis then names the regime. The adopter's counsel owns every one of those rows;
- **confidential supervisory information handling**: whether, and to whom, the contents of a
  supervisory request and the firm's response may be disclosed inside the institution. This
  service records and routes; it makes no disclosure decision;
- **legal professional privilege**: the engine flags a privileged document and holds it with a
  stated basis. It does not decide whether privilege is properly asserted, and it cannot: that is
  a lawyer's call on the document's content. The withholding schedule exists so a lawyer can
  overturn the hold, and the checker, not the code, is the control;
- **the silent-withhold asymmetry**: `policy.silent_withhold_tags` ships with the
  suspicious-activity tag, so that schedule row carries an identifier and a basis and no title. In
  several regimes the existence of such a filing is itself restricted. That is a legal position
  the adopter's counsel must confirm before deployment, which is why it is configuration and not a
  constant;
- **every number in the `policy:` block**: the response windows, the review buffer, the
  extension-notice period, the staleness window, the band ceilings, the completeness floor for
  release and the holiday calendars. All of it is reference policy, none of it is legal advice,
  and the completeness floor in particular ships at the strictest value as a default to ARGUE
  with rather than as a recommendation.
